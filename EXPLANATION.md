# EXPLANATION — Every file & how it all works

This document explains the **whole project**, top to bottom: what each file does,
what each part of the code does, how data flows through the system, which models
are used and why, and the key concepts. Read this and you can explain any part.

---

## 1. What this project is (in one paragraph)

A **multimodal search engine** for company documents. You ask a question in plain
English (or upload an image), and it finds the right document — **even when the
answer lives inside a chart, diagram, or screenshot**, not in typed text. It does
this by using a **vision model (Qwen-VL)** to "read" every image into text, then
searching everything by *meaning* using **embeddings + a FAISS vector index**.
It also **writes a short answer** grounded in the retrieved documents, and it
proves its value by comparing against a **text-only baseline** with real metrics.

---

## 2. The 30-second big picture

```
                       ┌──────────────── INGESTION (done once) ────────────────┐
   22 documents  ──▶   │  PDFs → extract text                                  │
   (PDFs + images)     │  every image/page → Qwen-VL writes a text caption     │
                       │  → save all "passages" (text + captions) to disk       │
                       └───────────────────────────┬───────────────────────────┘
                                                   │  embed each passage (OpenAI)
                                                   ▼
                                   ┌──── FAISS vector index (the "memory") ────┐
             TEXT-ONLY baseline ◀──┤  text passages only                       │
             MULTIMODAL         ◀──┤  text passages + image captions           │
                                   └───────────────────┬───────────────────────┘
                                                       ▲
   You ask: "Which server is overloaded?" ── embed ───┘
                                                       │
                                                       ▼
                          top matching documents  →  💡 LLM writes an answer
```

**Two ideas make it work:**
1. **Captioning** turns pixels into searchable text (that's how images become findable).
2. **Embeddings** turn text into numbers that capture *meaning*, so search matches
   ideas, not just keywords.

## 4. Deep dive — `rag.py` (the heart of everything)

This one file *is* the whole engine. It has **5 sections + the answer generator**.

### Section 1 — CONFIG (lines ~32–95)
- Defines **paths** (where the corpus, index, reports live).
- `_load_dotenv()` — reads your `.env` file so secrets/settings load automatically.
- Settings (each has a safe default): `OPENAI_API_KEY`, `OLLAMA_MODEL`
  (`qwen2.5vl:3b`), `OLLAMA_EMBED_MODEL` (`mxbai-embed-large`), `TOP_K`,
  `MAX_PDF_PAGES` (cap pages per PDF so captioning isn't endless), `FORCE_REBUILD`.
- `config_summary()` — a snapshot of the active config (shown in the app sidebar).

### Section 2 — EMBEDDINGS (turn text → numbers)
- **`MockEmbeddings`** — a keyless, offline fallback (keyword-hashing). Lets the
  app run with *zero* setup so it never crashes.
- **`get_embeddings()`** — picks the best available, in priority order:
  1. **OpenAI** `text-embedding-3-small` (if you have a key) — 1536-dim, semantic.
  2. **Local Ollama** `mxbai-embed-large` (if Ollama is running) — free, strong.
  3. **Mock** (last resort).
- *Why an interface?* So the same code works with a cloud model, a local model,
  or nothing — a **graceful-degradation** design.

### Section 3 — VLM (the vision model that reads images)
- **`CAPTION_PROMPT`** — the instruction telling the model *how* to describe an
  image for search ("include titles, chart values, table contents, colors…").
- **`VLM`** (abstract base) with two jobs: `caption()` (describe an image) and
  `rerank()` (score how relevant an image is to a query, 0–10).
- **`ChatOllamaVLM`** — **Qwen2.5-VL** running locally via Ollama. **This is the
  primary, mandated model.** Handles high-res images (downscales + bigger context
  window so it doesn't overflow).
- **`OpenAICompatVLM`** — the *same* logic over any OpenAI-compatible vision API
  (OpenAI `gpt-4o-mini`, or a hosted Qwen-VL via OpenRouter). Used as the cloud
  option / fallback.
- **`get_vlm()`** — priority, **Qwen-VL first at every tier**:
  1. Qwen-VL local (Ollama) → 2. Qwen-VL hosted API → 3. OpenAI vision → 4. mock.

### Section 4 — INGESTION (documents → searchable "passages")
- **`_chunk()`** — splits long PDF text into ~500-char pieces.
- **`_render_pdf_pages()`** — turns each PDF page into an image (for captioning +
  thumbnails), capped at `MAX_PDF_PAGES`.
- **`passages_for_file()`** — for ONE document, produces:
  - `text` passages (from PDF text), and
  - `caption` passages (Qwen-VL's description of each page/image).
  - Standalone images produce **only a caption** (no text) — that's *why* the
    text-only baseline is blind to them.
  - Uses a **caption cache** so re-running only captions *new* pages (resumable).
- **`build_index()`** — runs the above over all 22 docs → writes
  `data/index/passages.json`. This is the **expensive step** (the VLM calls).
- **`load_passages()`** — reads that file back.

### Section 5 — RETRIEVAL (the actual search)
- **`SearchHit` / `SearchResult`** — data holders for a result and a whole query.
- **`_faiss_available()` / `VECTORSTORE`** — use **FAISS** if installed, else fall
  back to LangChain's in-memory store (so it never crashes on a missing library).
- **`Pipeline`** — the search engine. The trick: **one class, two instances**:
  - `include_captions=True` → **multimodal** (searches text + image captions)
  - `include_captions=False` → **baseline** (text only)
  - Same code, so the comparison is **fair by construction**.
  - `build()` / `add_passages()` — put documents into a **FAISS** index.
  - `save()` / `load()` — persist/load the FAISS index (so the cloud loads it
    instead of re-embedding 250 passages at startup).
  - `search_text()` — embed the query → FAISS cosine search → dedupe by document.
  - `search_image()` — caption the uploaded image (VLM) → then search_text on that.
  - `_rerank()` — optional: the VLM *looks at* each candidate image and scores it;
    final score = `0.5·cosine + 0.5·visual_score`.
- **`generate_answer()`** — the **"generation" half of RAG**: sends the top
  retrieved documents + your question to an LLM (OpenAI, else Ollama) with strict
  instructions to answer **only** from those documents (no hallucination).
- **`build_pipelines()`** — the entry point the app calls. If a saved FAISS index
  exists, it **loads** it (fast, no embedding); otherwise it builds one.
- **`save_prebuilt_index()`** — `python rag.py save-index` builds + saves the
  FAISS index so it can be committed and loaded on a GPU-less host.

## 5. Deep dive — `app.py` (the website)

Built with **Streamlit** (Python's one-command web-app framework — it's the
frontend AND backend in one; `streamlit run app.py` runs everything).

- **Custom CSS** — the dark theme, gradient header, result cards, the green
  **Answer box**, relevance meters.
- **`_load()`** — builds/loads the two pipelines once (cached).
- **`_resolve()` / `_img_uri()`** — find image files and embed them in the page
  (works both locally and in the cloud via portable paths).
- **Header** — title + a live status pill (which engine is active).
- **Sidebar** — the engine info, the corpus list, an **upload** box (add your own
  docs live), and a "rebuild index" button.
- **Search controls** — Text/Image toggle, a **Model** selector (Qwen-VL /
  OpenAI vision — the one you pick reads the image AND reranks), an **Enable
  rerank** toggle, and the Top-K slider.
- **Results section** — the flow when you hit Search:
  1. If image query → the chosen model **reads the image** into text.
  2. **💡 Answer box** — the LLM answers your question from the top documents.
  3. **Side-by-side cards** — 🟣 Multimodal vs ⚪ Text-only baseline, each with a
     thumbnail, relevance meter, and the matched snippet. A ★ BEST MATCH ribbon
     marks #1; a "weak match" warning appears for nonsense queries.

## 6. Deep dive — `evaluate.py` (the proof)

- Loads the **18 labelled queries** (`data/queries.json`), each with the known
  correct document(s), and 11 flagged as "answer lives in an image."
- Runs every query through **both** pipelines and computes:
  - **Recall@1/3/5** (did a correct doc make the top-K?),
  - **MRR** (how high was the first correct doc?),
  - **nDCG@5** (rank quality),
  - **latency** per query.
- Reports **overall** and on the **image-answer subset**, then writes
  `reports/eval_report.md` with a table + an honest discussion of where multimodal
  helped and where it didn't.
- **Result:** multimodal **100% Recall@1** vs the baseline's **50% overall / 18%
  on image questions** — because the baseline is *structurally blind* to
  image-only documents.

## 7. Deep dive — `make_corpus.py` (the data)

- Generates **12 engineered documents** with `matplotlib` + `reportlab` + `Pillow`:
  text-rich policies, mixed prose+chart PDFs, and **visual-only** images (an org
  chart, a scanned salary table, a server dashboard, a network diagram) — deliberately
  planting answers that live *only in pixels* so multimodal can measurably win.
- **`fetch_real_docs()`** downloads **10 real open documents** — arXiv papers
  (Transformer, ResNet, BERT, ViT, GPT-3, word2vec) and Wikimedia images (internet
  map, sunspot chart, DNA diagram, Moore's-law chart) — for **corpus realism**.
- Writes `corpus_manifest.json` (the ground truth).

## 9. How to run it (locally)

```powershell
# one-time setup
pip install -r requirements.txt

# 1. make the sample documents
python make_corpus.py

# 2. read every image with Qwen-VL + build the searchable index
python rag.py            # (needs Ollama running for Qwen-VL)

# 3. measure multimodal vs text-only
python evaluate.py

# 4. launch the website
streamlit run app.py     # opens http://localhost:8501
```

**No separate backend** — Streamlit is the whole app. The only extra thing that
must be running is **Ollama** (for Qwen-VL image reading). Text search works with
just the OpenAI key.

## 10. Models used (and why)

| Job | Model | Why |
|---|---|---|
| **Read images → text** | **Qwen2.5-VL** (local, via Ollama) | *Mandated*; free & private; the primary vision model |
| Read images (cloud option) | OpenAI `gpt-4o-mini` vision | Faster; used when there's no local GPU |
| **Text → embeddings** | OpenAI `text-embedding-3-small` (1536-dim) | Top quality; `mxbai-embed-large` is the free local fallback |
| **Write the answer** | OpenAI `gpt-4o-mini` (or local Qwen) | Grounded generation from retrieved docs |
| **Store/search vectors** | **FAISS** (exact cosine) | Real vector index; fast at this scale |
| Orchestration | **LangChain** | Documents, Embeddings, VectorStore, ChatOllama |
| UI | **Streamlit** | *Mandated*; one-command web app |

## 11. Key concepts (glossary)

- **Embedding** — a list of ~1,536 numbers representing a piece of text's *meaning*.
  Similar meanings → similar numbers. This is how search matches ideas, not keywords.
- **Vector search / FAISS** — finding the embeddings closest to your query's
  embedding (by cosine similarity). FAISS is the library that stores & searches them.
- **RAG (Retrieval-Augmented Generation)** — *Retrieve* the relevant documents,
  then *Generate* an answer grounded in them (so the LLM can't make things up).
- **VLM (Vision-Language Model)** — a model like Qwen-VL that can *look at images*
  and describe/reason about them.
- **Multimodal** — handling more than one type of data (here: text **and** images).
- **Reranking** — a second, smarter pass that re-scores the top candidates (here,
  the VLM looks at the actual images).
- **Baseline** — the simple system you compare against (text-only RAG) to *prove*
  your system is better with numbers.

## 12. The design decisions worth explaining (interview gold)

- **Local vs API** → local-first (Qwen-VL + optional local embeddings) for free,
  private, reproducible; a reasoned API choice scores the same.
- **Embedding strategy** → *parsed-text + image-caption* (unifies text and pixels
  in one vector space; makes Qwen-VL load-bearing). Gave up fine visual similarity
  a CLIP-image-embedding hybrid would add.
- **Vector store** → FAISS *flat* (exact) because at ~250 vectors, approximate
  search buys nothing; at 100k+ we'd switch to HNSW/IVF.
- **Fair comparison** → multimodal and baseline share one `Pipeline` class,
  differing only by whether captions are indexed.
- **Graceful degradation** → missing key/Ollama → mock fallback, never a crash.
- **Cloud** → commit the FAISS index so the app *loads* it instead of re-embedding
  at startup (which is flaky on free tiers).
